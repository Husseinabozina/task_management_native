# CLOUD_PLAN — خطة السحابة والفريق (مسودة للنقاش — لم يُنفذ منها شيء)

الحالة: **مسودة تخطيط v1 (2026-10-04)** — قرار البنية المعلق على المستخدم. لا implementation قبل اعتماد هذه الخطة وتحديد الخيار.
المرجع: رؤية Hussein الأصلية — «محلي أولًا وجهزه بحيث لو عاوزنا نخليه سحابي نخليه» + «لفريق». الحقول المحجوزة في `DATA_CONTRACTS.md` (ownerId/workspaceId/revision) كانت مصممة لهذه اللحظة.

## 1) الهدف على مراحل

| المرحلة | ما تضيفه | خارجها عمدًا |
|---|---|---|
| C1 — حساب ومزامنة شخصية | تسجيل دخول (Email + Apple) + نسخ المهمة/المشروع للسحابة + مزامنة بين أجهزة نفس المستخدم | مشاركة، فريق، realtime |
| C2 — تصلب المزامنة | حل تعارض revision، tombstones للحذف، إعادة محاولة ووضع offline، تصدير نسخة احتياطية | لوحات إدارية |
| C3 — الفريق | Workspaces + دعوات + صلاحيات (مالك/محرر/قارئ) + مشاريع مشتركة | تعديل آني متزامن (realtime cursors) |

## 2) الوضع الراهن (حقائق متحققة)

- كل القراءات/الكتابات تمر عبر `TaskRepository`/`ProjectRepository` — إضافة تنفيذ سحابي لا يمس أي شاشة (D2).
- `id` = UUID ثابت لكل صف → صالح كمفتاح مزامنة عالميًا دون تحويل.
- `updatedAt` موجود ويتحدث في كل mutation؛ `status/priority` مخزنة كقيم خام نصية قابلة للنقل.
- التذكيرات **ملكية للجهاز** (جدولة UNUserNotificationCenter محلية) — لن تُزامَن كسلوك، لكن `reminderDate` نفسه يُزامَن كبيانات.
- SwiftData مخزن محلي مصدر الحقيقة أثناء عدم الاتصال — السحابة **طبقة مزامنة وليست بديلًا** عنه (لا dual source of truth).

## 3) خيارات البنية — المقارنة

| المعيار | **Supabase (توصيتي)** | Firebase/Firestore | CloudKit | Custom (NestJS+Postgres) |
|---|---|---|---|---|
| تطابق النموذج مع عقودنا | Postgres جداول تعكس TaskItem/ProjectItem 1:1 | NoSQL — إعادة تصميم مستندات | قيود: لا unique constraints (id!) ولا علاقات كاملة | كامل التحكم |
| Auth | Email + Apple + Google جاهزة | ممتازة | Apple ID فقط 🔒 | من الصفر |
| مرحلة الفريق (C3) | Row-Level Security + دوال SQL — قوية | Security Rules بـNoSQL أصعب في التدقيق | مشاركة محدودة | يدوي بالكامل |
| مسار أندرويد لاحقًا (D1) | ✅ REST/SDK رسمي | ✅ | ❌ مستحيل عمليًا | ✅ |
| كود المزامنة عندنا | نكتبه يدويًا (revision-based) | مبني داخليًا لكن يتعارض مع local-first | مدمج مع السواتر | نكتبه يدويًا |
| Lock-in | متوسط (Postgres مفتوح — الهجرة ممكنة) | مرتفع | كلي | صفر |
| التكلفة/التشغيل | Free tier كافٍ للبداية + self-host ممكن | Free tier | مجاني مع الجهاز | سيرفر تشغيل وتكلفة وقت |

**التوصية**: Supabase. الأسباب الحاسمة: (1) أقرب نموذج بيانات لعقودنا فتبقى حدود الـ repository صادقة، (2) يدعم مرحلة الفريق بـ RLS بدل كتابة صلاحيات يدوية، (3) لا يغلق باب أندرويد (D1)، (4) Postgres مفتوح = هروب ممكن إلى custom backend بنفس السكيما لو احتجنا.
**مرفوض**: CloudKit (يقفل أندرويد + قيود السكيما تكسر `id` الفريد)؛ Firebase (dual source of truth مع SwiftData + إعادة نمذجة NoSQL).
**ملاحظة صدق**: supabase-swift SDK مجتمعي (ليس رسمي بحجم Firebase) — مخاطرة مقبولة لأن التكامل من طرفنا محصور في REST + Auth.

## 4) السكيما المقترحة (C1)

```sql
workspaces(id uuid pk, name text, owner_id uuid, created_at timestamptz)   -- C3
profiles(id uuid pk = auth.users.id, display_name text, avatar_url text)   -- C3
tasks(id uuid pk, workspace_id uuid, owner_id uuid, title text, details text,
      status text, priority text, is_pinned bool, due_day date, project_id uuid,
      reminder_date timestamptz, completed_at timestamptz,
      created_at timestamptz, updated_at timestamptz,
      revision bigint, deleted_at timestamptz)                             -- deleted_at = tombstone
projects(id uuid pk, workspace_id uuid, owner_id uuid, name text, emoji text,
         color_key text, created_at timestamptz, revision bigint, deleted_at timestamptz)
```
- C1: كل صفوف المستخدم في workspace شخصي تلقائي (auto-create عند أول login) — C3 يضيف مشاركة الـ workspace.
- RLS (C1): `owner_id = auth.uid()` على كل العمليات. (C3): سياسات membership.
- تعارضات: `revision` يتزايد server-side عند كل كتابة؛ العميل يرسل `updated_at + revision` المتوقعة؛ اختلاف = تعارض → **LWW على مستوى الصف** (آخر updated_at يفوز) + تسجيل الحالة المتعارضة في عمود audit لمرحلة C2 إن احتجنا رفعًا.

## 5) استراتيجية المزامنة (C1 — أبسط شكل صادق)

- **Push**: كل mutation محلي يُسجل في `Outbox` (جدول محلي SwiftData صغير) → worker يدفعه لـ Supabase عند توفر الشبكة (idempotent بالـ id).
- **Pull**: عند الإقلاع/العودة من الخلفية + periodic: جلب `updated_at > آخر مزامنة` وتطبيق ما هو أحدث.
- **الترتيب**: محليًا SwiftData يظل مصدر الحقيقة للعرض؛ السحابة مرآة. التطبيق يعمل offline كاملًا كما هو الآن (ثابت لا يُكسر — D2).
- **الحذف**: tombstone (`deleted_at`) لا حذف فعلي — عشان ينتشر الحذف بين الأجهزة.
- **التذكيرات**: تبقى جدولة محلية لكل جهاز من البيانات المزامنة (الجهاز يخلّص شغله بعد الـ pull) — لا إشعارات سيرفر في C1.

## 6) الهجرة من المحلي (أخطر خطوة — لها بروتوكول خاص)

1. عند أول login: نسخة احتياطية محلية إلزامية (تصدير store file) قبل أي لمسة.
2. كل الصفوف المحلية تأخذ `owner_id` للمستخدم وترفع دفعة واحدة (idempotent بالـ UUID — إعادة المحاولة آمنة).
3. لا يُمسح شيء محليًا أبدًا في الهجرة — الرفع فقط.
4. معيار قبول C1: جهازان بنفس الحساب يشوفان نفس المهام، وقطع الشبكة لا يكسر شيئًا، والمهام القديمة كلها موجودة بعد الرفع (عدّ مطابق).

## 7) المخاطر الصريحة

| الخطر | التخفيف |
|---|---|
| فقدان بيانات في الهجرة | نسخة احتياطية إلزامية + عدّ مقارن قبل/بعد + مرحلة تجربة على حساب تجربة أولًا |
| تعارضات مزامنة غير متوقعة | LWW بسيط موثق + revision audit — والتعقيد الإضافي مؤجل لـ C2 بعد قياس حقيقي |
| supabase-swft SDK مجتمعي | حصر التكامل في REST + Auth الأساسية؛ أي limitation = مخرجنا لـ custom backend بنفس السكيما |
| Keychain لتخزين التوكن | استخدام القياسي — لا توكن في UserDefaults إطلاقًا |
| الشاشات الجديدة (Login/Restore) | ممنوع أزرار ميتة: Login بلا backing = لا يُعرض؛ نبدأ بزر «تسجيل الدخول» واحد حقيقي فقط |

## 8) ما أحتاجه منك الآن (قرار واحد + موافقة)

1. **اعتماد Supabase** كبنية (أو ترجيح خيار آخر من الجدول — ناقشه).
2. **اعتماد تدرج C1→C2→C3** ببدء التنفيذ من C1 فقط بعد اكتمال V1 الحالية واستقرارها بتجربتك.

## 9) أين أحتاج دعمًا أقوى (بصراحة)

- **كتابة محرك المزامنة نفسه** (outbox + pull + تعارضات): قابل للتنفيذ مني، لكن مراجعته بمعايير إنتاجية — أنصح بجلسة مراجعة بموديل أقوى أو على الأقل مراجعتك المتأنية معايا سطر سطر.
- **قواعد RLS لمرحلة الفريق (C3)**: أخطاء الصلاحيات صامتة وخطيرة — تُكتب وتُراجع مرتين.
- تخطيط الاختبارات اليدوية للسيتاريوهات (جهازان + طيران + حذف متزامن): سأكتبها كـ checklist تنفذها أنت بنفسك.
