# دليل تنفيذ تطبيق إدارة مهام مع zcode

## هدف الدليل وطريقة استخدامه

هذا دليل عمل قابل للتنفيذ لمساعد برمجي: من تعريف المنتج إلى تصميم الواجهة، تنظيم الكود، حفظ البيانات، والتسليم. مبني على قرارات وتجارب مشروع الشات، مع تكييفها لتطبيق إدارة مهام. ليس نسخة من متطلبات تطبيق الشات.

المستخدم هو من يشغّل التطبيق على الـSimulator أو الجهاز ويقيّم الشكل. المساعد يكتب الكود، يراجع مصادره وينفذ الفحوصات المسموح بها، ثم يقدم تعليمات واضحة للمستخدم عندما يطلب التشغيل.

اختيار المستخدم هنا هو **Native**. مسار iPhone يستخدم Swift/SwiftUI، ومسار Android يستخدم Kotlin/Jetpack Compose. لم تُحسم المنصة بعد؛ على المساعد تحديدها قبل إنشاء المشروع. لو اختير الاثنان، فهما تطبيقان بواجهات وكود Native منفصلين، مع عقود منتج مشتركة؛ لا يبدأ مسارين بالتوازي دون نطاق واضح. الأمثلة المعمارية اقتراحات، ولا تعني الموافقة على ميزات أو خدمات لم يطلبها المستخدم.

هذا الدليل مفصّل كي يعتمد المساعد على خطوات وقواعد واضحة. لا يفترض معرفة قدرات أو حدود نموذج معين. تاريخ الإعداد: ٢ أكتوبر ٢٠٢٦؛ أرقام SDK والواجهات المتغيرة تُراجع من المشروع والوثائق الرسمية وقت التنفيذ.

**اقرأ أقسام ١–٤ أولًا، ثبّت نطاق الإصدار الأول، ثم نفّذ مرحلة واحدة في كل مرة.** عند العودة للمشروع اقرأ CURRENT_STATE بدل محاولة استنتاج الحالة من محادثة طويلة.

## ١. تعليمات ملزمة للمساعد

1. لا تشغّل Simulator أو Emulator، ولا تتحكم في جهاز المستخدم أو تلتقط شاشة التطبيق. لا تثبّت التطبيق ولا تبدأ بناء iOS/Android أو xcodebuild أو Gradle assemble/install أو pod install تلقائيًا. تشغيل التطبيق ومعاينته للمستخدم، إلا إذا طلب منك هو ذلك صراحة لاحقًا.
2. لا تشغّل dev server أو قاعدة بيانات أو عملية طويلة بالخلفية تلقائيًا. إذا طلب المستخدم تشغيل خدمة، سجّل المنفذ والعملية وطريقة إيقافها. لا تفترض أنها تظل شغالة بعد إعادة تشغيل الجهاز.
3. لا تضف ولا تشغّل اختبارات افتراضيًا، حتى الموجودة، إلا إذا طلب المستخدم التحقق بها. الوضع الأولي مراجعة المصادر وفحوص التنسيق وlint المتاحة. تحقق الأنواع في Native قد يحتاج compilation؛ لا تدّعِ تنفيذه من مراجعة النص أو formatter. فشل فحص قائم ظهر في المشروع لازم يتفهم ويتعالج؛ لا تحذف الفحص لإخفاء المشكلة.
4. لا تدخل في تجهيز Xcode، CocoaPods، Android SDK أو تنزيلات native كبيرة عشان تقول إنك راجعت التصميم. سجّل native build وvisual acceptance كأشياء لم تُنفذ.
5. لا تعمل upgrade للتقنيات أو تغيّر dependencies لمجرد وجود نسخة أحدث. اقرأ نسخة المشروع والـSDK الفعلي أولًا. أضف dependency فقط عندما تخدم حاجة حالية محددة.
6. لا تستخدم force push، ولا تدمج أو تغلق PR، ولا تنشر خدمة أو repository عامة من غير تفويض المستخدم. التفويض القائم في نفس المهمة يظل صالحًا؛ لا تطلبه مرة أخرى.
7. حافظ على تعديلات المستخدم والملفات غير المنشورة. لا تستخدم git reset --hard أو clean، ولا تقتل عمليات بناء عامة، ولا تمسح قاعدة بيانات لتسهيل التنفيذ.
8. لا تغيّر architecture أو سلوك المنتج أثناء إصلاح بصري صغير إلا إذا ثبت أن التغيير ضروري وتم توضيح أثره.
9. لا تصف mockup مولّدًا أو مراجعة الكود بأنه screenshot للتطبيق أو قبول بصري. لا تصف تحليل الكود بأنه إثبات أن التخزين أو التطبيق اشتغل فعليًا.
10. لا تعرض زرًا أو إعدادًا يوحي بميزة غير منفذة. كل عنصر تفاعلي له سلوك محدد، أو يُستبعد من هذه المرحلة.
11. نفّذ المهمة المتفق عليها حتى نهايتها. الاختيارات الصغيرة المحلية قرارك؛ أسئلة المستخدم تقتصر على نقص يؤثر في المنتج أو يغيّر اتجاه العمل.
12. بعد كل checkpoint حدّث CURRENT_STATE. وضّح ما نُفذ، وما تم فحصه فعلًا، وما بقي، والخطوة التالية الواحدة.

هذه حدود التشغيل لهذا المشروع، ويمكن للمستخدم تعديلها صراحة. أي قيد صريح جديد من المستخدم يُسجّل ويُحترم.

## ٢. فهم الفكرة قبل كتابة الكود

ابدأ بوصف المنتج في سطر: «تطبيق يساعد شخصًا على جمع مهامه، ترتيبها، ومعرفة ما عليه اليوم، ثم إتمامها بسهولة».

احسم أربعة أشياء من الطلب والمشروع الموجود:

| القرار | الخيارات | أثره |
|---|---|---|
| المنصة | iPhone: SwiftUI / Android: Compose / كلاهما Native | يحدد الأدوات وحدود التوافق وكود الواجهة |
| المستخدمون | شخص واحد / فريق | الفريق يحتاج عضوية وصلاحيات وعقود مشاركة |
| حفظ البيانات | محلي / حساب سحابي / مزامنة | يحدد التخزين، auth وسياسة التعارض |
| الهدف الحالي | تجربة منتج / إصدار أول | يحدد حدود الجودة والتسليم |

إذا لم يمكن استنتاج القرارات، اسأل أسئلة قصيرة مجمّعة، ثلاث أسئلة كحد أقصى. واصل قراءة المشروع وتسجيل ما هو معروف أثناء انتظار الرد؛ لا تبنِ backend أو auth بناءً على إجابة لم تصل.

**اقتراح بداية خفيف للمناقشة:** تطبيق شخصي، منصة واحدة، حفظ محلي دائم، دون auth أو مشاركة فريق. هذا اقتراح وليس نطاقًا معتمدًا تلقائيًا. لو طلب المستخدم حسابًا سحابيًا، نحدد backend/auth منذ البداية.

اكتب PRODUCT_BRIEF وفيه: المستخدم المستهدف، المشكلة، أهم ثلاث رحلات، نطاق V1، المستبعد حاليًا، معيار نجاح التجربة، والقرارات التي تحتاج إجابة.

## ٣. تعريف الميزات بدقة

لكل ميزة سجّل: هدف المستخدم، المدخلات، ما يحدث عند الضغط، أين تُحفظ البيانات، حالات النجاح والخطأ، وشروط قبولها.

**قائمة مرشحة لـV1، تختار منها مع المستخدم:**

| الميزة | التعريف المطلوب | شرط قبول واضح |
|---|---|---|
| قائمة المهام | عرض المهام وترتيبها وحالة كل مهمة | تظهر المهام المحفوظة، ومعها حالة فارغة مفهومة |
| إنشاء مهمة | عنوان، وصف اختياري، أولوية، تاريخ اختياري | العنوان لا يكون فارغًا؛ يظهر العنصر بعد حفظ ناجح |
| تعديل مهمة | تعديل نفس العنصر مع الحفاظ على هويته | التغيير يخص المهمة المحددة ويظل محفوظًا |
| إتمام / إعادة فتح | تغيير الحالة في الاتجاهين | completedAt يتغير حسب القاعدة المتفق عليها |
| موعد المهمة | اليوم / القادم / متأخرة، إذا كانت ضمن النطاق | التصنيف يعتمد على قاعدة تاريخ معلنة |
| مشروع أو قائمة | تجميع المهام تحت مشروع اختياري | حذف مشروع لا يمسح مهامه بطريق غير متفق عليه |
| البحث والفلاتر | البحث بالعنوان وتصفية الحالة والأولوية | no results مختلف عن عدم وجود مهام أصلًا |
| الأرشفة / الحذف | تحدد لكل فعل أثره وإمكانية الرجوع | المستخدم يفهم الفرق ولا يفقد بيانات بالخطأ |
| Settings | إعدادات لها تنفيذ حقيقي | كل اختيار يطبّق ويحفظ وفق المتطلبات |

**ميزات تحتاج checkpoint مستقل إذا طُلبت:** تذكيرات فعلية، recurrence، subtasks، drag and drop، ملفات، مشاركة فريق، حسابات سحابية، مزامنة offline، integrations، ذكاء اصطناعي.

لا تضف هذه الميزات إلى V1 لمجرد أنها شائعة في تطبيقات إدارة المهام. قابلية التوسع تعني حدودًا جيدة يمكن إضافة الميزات عندها، وليست تنفيذ كل الميزات مبكرًا.

### ثلاث رحلات أساسية

- إنشاء: القائمة → إضافة → إدخال عنوان → حفظ → ظهور المهمة بالمعلومات الصحيحة.
- إتمام: مهمة نشطة → إتمام → عرض حالة مكتملة → إعادة فتح عند الطلب.
- تنظيم: بحث أو فلتر → فتح مهمة → تعديل الأولوية/الموعد/المشروع → انعكاس التغيير على القائمة.

اكتب الرحلات بنص بسيط قبل أسماء الكلاسات. أضف الحسابات أو التذكيرات إلى الرحلات فقط إذا كانت ضمن النطاق المعتمد.

## ٤. بوابة البداية: المشروع الحالي هو الحقيقة

لو المشروع موجود، اقرأ AGENTS والتعليمات، README، الملفات الفعلية، branch وHEAD وgit status، manifests وlockfiles، config وCI. لا تفترض أن كلام محادثة قديمة يصف HEAD الحالي.

سجّل:

- مسار المشروع الفعلي، وليس نسخة قديمة أو رابطًا غير معروف.
- الفرع وHEAD وآخر checkpoint.
- الملفات المحلية المتغيرة قبل عملك ومالكها إن عُرف.
- في iOS: Xcode/Swift الفعليان، deployment target، ملفات المشروع وPackage.resolved عند وجوده. في Android: JDK/Kotlin/Gradle/AGP وSDK المطلوبة، Gradle wrapper وversion catalog والـlockfiles عند وجودها.
- طريقة حفظ البيانات الحالية وحدودها.
- الفحوصات الموجودة ونتائجها السابقة: تاريخية أم على HEAD الحالي؟

لو المشروع جديد، أنشئ الأساس الصغير المناسب للنطاق. لا تنسخ configs أو package.json أو أرقام إصدارات تطبيق الشات إلى مشروع مختلف.

**درس من تجربتنا:** وقع اختلاف بين Flutter الموجود في PATH وبين SDK الذي يدعم مشروع الشات. في Native راجع بالمثل Xcode المختار ونسخة Swift، أو JDK الذي يستخدمه Gradle والـIDE. لا تخفّض متطلبات المشروع لإرضاء أداة أقدم اختيرت بالخطأ، ولا تبدأ تنزيل SDK كبيرًا قبل تحديد المشكلة.

## ٥. ملفات تحفظ القرارات وتمنع فقدان السياق

اجعل التوثيق قصيرًا وحديثًا. استخدم هذا الهيكل كبداية؛ أضف الملف فقط عند وجود محتوى فعلي له:

```text
docs/
  product/
    PRODUCT_BRIEF.md
    FEATURE_SCOPE.md
    USER_FLOWS.md
  design/
    UI_DIRECTION.md
    SCREEN_PLAN.md
    DESIGN_SYSTEM.md
  architecture/
    ARCHITECTURE.md
    DATA_CONTRACTS.md
    DECISIONS.md
  project/
    CURRENT_STATE.md
    BACKLOG.md
    HANDOFF.md
```

- FEATURE_SCOPE: المعتمد، المقترح، المؤجل؛ لا تخلط الحالات.
- UI_DIRECTION: مرجع الشكل المعتمد وتاريخ القرار، وأي أمثلة مجرد اقتراحات.
- DATA_CONTRACTS: معنى الحقول والعمليات والأخطاء.
- DECISIONS: القرار، السبب، البدائل المؤثرة، ومتى يُعاد النظر فيه.
- CURRENT_STATE: ماذا يوجد فعلًا وما الذي لم يُفحص.
- HANDOFF: ما يحتاجه مساعد آخر ليكمل من مكان صحيح.

إذا اختلفت الملفات، راجع تواريخها والكود وقرارات المستخدم. صحّح التعارض؛ لا تضف مستندًا جديدًا يعيد نفس التضارب.

## ٦. Architecture عملية وقابلة للتوسع

### القاعدة الأساسية

الواجهة تعرض الحالة وترسل نية المستخدم. منطق المنتج يتعامل مع أنواع وعقود مستقلة. تنفيذ التخزين أو HTTP يعيش في طبقة البيانات. تركيب الاعتماديات يتم في مكان واضح عند بدء التطبيق.

```text
Task screen → Task state/controller → TaskRepository contract
                                      ↑
                         Local or remote implementation
```

الدومين لا يستورد SwiftUI أو Compose أو Android Context أو HTTP أو ORM أو SDK خاص بمصدر البيانات. الأنواع القياسية للمنصة مسموحة؛ الهدف استقلال قواعد المنتج عن الواجهة وطريقة التخزين.

### مثال iPhone: Swift/SwiftUI

```text
TaskManagement/
  App/
    TaskManagementApp.swift
    AppDependencies.swift
    AppRouter.swift
  Shared/
    DesignSystem/
    Errors/
    Time/
  Features/
    Tasks/
      Domain/
        TaskItem.swift
        TaskRepository.swift
      Data/
        PersistedTask.swift
        LocalTaskRepository.swift
        TaskMapper.swift
      Presentation/
        TaskListModel.swift
        TaskListView.swift
        TaskEditorView.swift
        Components/
    Projects/
    Settings/
```

اسم TaskItem يتجنب خلط مهمة المنتج مع Swift concurrency Task. Domain entity قيمة بسيطة مستقلة، وPersistedTask خاص بالتخزين إذا احتاج المخزن نموذجًا مختلفًا. لا تسرّب ModelContext إلى Views عندما تعتمد هذا الفصل. استخدم حقنًا صريحًا للاعتماديات عند نقطة تركيب التطبيق؛ مكتبة DI ليست شرطًا.

### مثال Android: Kotlin/Compose

```text
app/src/main/java/<package>/
  app/                 # application, navigation, composition
  shared/              # design system, errors, time
  features/tasks/
    domain/            # TaskItem, TaskRepository
    data/              # TaskEntity, TaskDao, LocalTaskRepository, mapping
    presentation/      # TaskListViewModel, TaskUiState, TaskListScreen, TaskEditorScreen
  features/projects/
  features/settings/
```

هذا مثال حدود وليس أمرًا بإنشاء كل ملف ومجلد فورًا. لا تنشئ مجلدات فارغة. لو mapper غير مطلوب حاليًا فلا تختلقه. أنشئ use case مستقل عندما يحتوي قاعدة أو orchestration حقيقيًا؛ الاستدعاء البسيط لا يحتاج طبقات وسيطة متعددة.

### State management

- حافظ على pattern الموجود إذا كان صالحًا؛ في مشروع جديد اختر واحدًا بناءً على احتياجاته وسجّل السبب.
- حالة القائمة أو التحميل غير المتزامن تملكها screen model في SwiftUI أو ViewModel في Compose، وتُحقن فيه عقود البيانات.
- فتح قائمة صغيرة أو draft المحرر يمكن أن يظل local UI state، مع عمر واضح: لا تفقده عند تحديث عابر للواجهة. لا تكرر draft محفوظًا ونسخة شاشة دون قواعد مزامنة.
- لا تستخدم global controller يدير كل التطبيق، ولا تجعل كل View أو composable يتحدث مباشرة مع التخزين.
- لا تكرر نفس المهمة كمصدر حقيقة مستقل في أكثر من controller.

**iOS:** اختر Observation أو ObservableObject بما يناسب deployment target والمشروع القائم. دعم Observation داخل SwiftUI يبدأ من iOS 17؛ لا تستخدمه ثم تعلن دعم نسخة أقدم. حدّد مالك model وعمره، واحتفظ بالتحديثات التي تخص UI على MainActor. استخدم async/await وإلغاء العمل وفق عمر الشاشة؛ لا تجعل كل عملية Task.detached، ولا تنقل context التخزين بين actors بلا قواعد صحيحة. هذه توجيهات تصميم وليست إثبات compilation. [مرجع Apple لبيانات SwiftUI](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app).

**Android:** ViewModel يعرض UiState واضحة، والواجهة ترسل أفعال المستخدم. عند استخدام StateFlow اجمع الحالة بطريقة تحترم lifecycle. لا تضع Activity أو Context في domain أو screen ViewModel. استخدم coroutines وsuspend للعمليات التي تحتاجها، وألغِ البحث القديم بدل أن يكتب فوق الجديد. DI يدوي مناسب لبداية صغيرة؛ Hilt يُقيّم عند وجود احتياج فعلي. Google توضح أن طبقة domain/use cases تُضاف حسب تعقيد وإعادة استخدام المنطق، وليست إلزامية لكل شاشة. [توصيات Android الرسمية](https://developer.android.com/topic/architecture/recommendations).

### Repository contract صغير

حدد عمليات يحتاجها المنتج فقط: عرض المهام، جلب مهمة، إنشاء، تعديل، تغيير completion، أرشفة/حذف إذا كانا معتمدين. حدّد هل القائمة تُراقب عبر stream أم تُحدّث بعد mutation؛ اختر نهجًا واضحًا.

العقد يعيد domain entities/failures. لا يسرّب JSON أو database rows أو HTTP response إلى الواجهة. ابدأ implementation واحدًا حقيقيًا؛ إمكان تبديله لاحقًا يتحقق بالحدود، دون كتابة backend/local implementations غير مستخدمة الآن.

## ٧. عقد بيانات المهمة قبل الشاشة

الحقول التالية مثال يحتاج مواءمة مع النطاق:

| الحقل | المعنى والقاعدة |
|---|---|
| id | هوية ثابتة؛ لا تستخدم مكان العنصر في القائمة كهوية |
| title | مطلوب بعد trim؛ حد الطول متفق عليه |
| description | اختياري؛ حد الطول واضح |
| status | active أو completed في V1 إذا لم يطلب المستخدم workflow أوسع |
| priority | قيم محددة مثل low/normal/high؛ لا تخزن نصوص UI المترجمة |
| dueDate | تاريخ تقويمي اختياري إذا كانت الميزة «يوم» دون ساعة |
| projectId | رابط اختياري، مع سياسة حذف المشروع |
| createdAt / updatedAt | وقت إنشاء/تحديث؛ المصدر المسؤول عنهما محدد |
| completedAt | وقت الإتمام؛ يُزال عند إعادة الفتح إذا كانت تلك القاعدة المعتمدة |
| archivedAt | منفصل عن الإتمام إذا الأرشفة جزء من النطاق |
| ownerId | مطلوب في المنتج السحابي ذي الحسابات؛ ليس دليل صلاحية وحده |
| revision | يُضاف إذا احتاج عقد المزامنة حل التعارض؛ لا يُضاف زينة |

### التاريخ: خطأ سهل لكنه مؤثر

فرق بين موعد «٣ أكتوبر» وبين موعد «٣ أكتوبر الساعة ٩ صباحًا». التاريخ فقط يُحفظ كقيمة تقويمية، لا تحوّله إلى منتصف الليل UTC وتسمح بأن يتحول ليوم آخر. الموعد ذو الساعة يحتاج instant ومنطقة زمنية وقاعدة عرض واضحة.

إذا اليوم-only هو النطاق: overdue = موعد أقدم من اليوم وفق تقويم التطبيق، والمهمة غير مكتملة وغير مؤرشفة. الموعد الغائب لا يدخل اليوم أو المتأخرة تلقائيًا. القادم له حد متفق عليه، وليس تعريفًا يختلف بين الشاشات.

ضع قاعدة التصنيف والترتيب في مكان واحد. استخدم ID ثابتًا لكسر تعادل الترتيب عند الحاجة. لو backend موجود، حدّد هل التصنيف في query أم عند العميل، وحدود pagination والبحث.

### قواعد mutation

- Create لا يولّد عنصرًا ثانيًا مع كل retry إذا كان التخزين سحابيًا؛ اتفق على idempotency عند الحاجة.
- Edit يخص نفس id ويعيد القيمة المحفوظة، مع أثر الفشل واضحًا.
- Completion وتوقيته يتغيران معًا في عملية واحدة عند وجود قاعدة تربطهما.
- Archive ليس مرادفًا لـComplete؛ ظهور المؤرشف تحدده الفلاتر.
- Delete له confirmation أو Undo حقيقي حسب القرار؛ لا تعرض Undo شكليًا بعد حذف غير قابل للاسترجاع.
- الأزرار لا تقبل double submit أثناء عملية حفظ إلا لو العقد يعالجه.

## ٨. التخزين، offline، والـbackend عند الحاجة

### لو الإصدار محلي

اختيار مخزن مناسب للبيانات والعلاقات، مع IDs ومخطط ونسخة schema ومراجعة migrations عندما يتغير. قائمة in-memory ليست حفظًا دائمًا، وpreferences ليست بديلًا عامًا لقاعدة مهام مترابطة.

في iOS قيّم SwiftData مقابل Core Data حسب deployment target وطبيعة المشروع؛ اختر مخزنًا واحدًا، ولا تفعل CloudKit لمجرد اختيار التخزين. في Android يمكن استخدام Room مع Entity/DAO داخل data وmapping إلى domain. الاختيار يُسجّل بعد مراجعة التوافق، وليس بنسخ أحدث snippet. بيانات Settings البسيطة يمكن أن تستخدم آلية preferences المناسبة للمنصة. حفظ حالة التبويب ليس حفظ قاعدة المهام.

احفظ المهمة، اقرأ القيمة المحفوظة، ثم حدّث الحالة وفق النهج المختار. فشل الكتابة لا يتحول إلى نجاح UI. لا تمسح البيانات عند خطأ قراءة عام. الدليل لا يثبت بقاء البيانات بعد إعادة تشغيل التطبيق؛ هذا يحتاج تجربة المستخدم أو اختبار مصرح به.

### لو الإصدار سحابي

حدد REST contracts وownership وauth قبل تركيب الواجهة عليها. backend modular monolith مناسب كبداية لو الاحتياجات تسمح؛ لا تبدأ microservices لمجرد قابلية التوسع.

المسار: request validation → authorization → service → persistence → response. المستخدم لا يقرأ أو يعدل مهمة شخص آخر اعتمادًا على id أرسله العميل. قيود البيانات والمعاملات تعالج العمليات المركبة.

صف معنى local draft، optimistic update، retry، timeout، conflict وlogout. فشل شبكة لا يعني تلقائيًا حذف session. إن لم تُنفذ مزامنة offline/outbox، لا تصف التطبيق أنه يدعمها.

أضف realtime فقط إذا كان التعاون المتزامن مطلوبًا وبعد صحة الحفظ. أحداث التحديث تتبع نجاح التخزين؛ الاتصال الحي ليس مصدر الحقيقة الدائم.

### الديمو

للمعاينة يمكن توفير demo data عبر مدخل واضح منفصل، أو seeder idempotent عندما يُطلب. لا تمسح بيانات المستخدم ولا تخلط بيانات تجريبية مخفية بالبيانات الحقيقية. لا تنشر credentials أو tokens في التقرير أو Git.

## ٩. UI/UX قبل التوسع في الشاشات

لا تبدأ بعشرين شاشة. ابدأ بشاشة القائمة ومحرر المهمة، وحدّد اتجاهًا بصريًا واحدًا قابلًا للمراجعة. لو توجد صور مرجعية، سجّل ما المطلوب تقليده: توزيع، ألوان، خط، كثافة، شكل الأيقونات؛ ولا تستنتج ميزة منتج من كل زر في صورة المرجع.

لا تنقل ألوان ولوجو وزخارف تطبيق الشات تلقائيًا. تطبيق المهام له شخصية تختارها مع المستخدم: وضوح وهدوء وتركيز، مع هوية بصرية مميزة تخدم الاستخدام.

### Design system صغير

- ألوان معنوية: background / surface / text / secondary text / accent / border / success / warning / error.
- درجات خط: عنوان شاشة، عنوان مهمة، body، metadata. أسماء المهام والمواعيد تحتاج قراءة واضحة.
- مسافات متسقة؛ مثال مبدئي 4، 8، 12، 16، 24، 32 مع استخدام فعلي.
- radius وحدود وظلال مختارة؛ لا تخترع style جديدًا في كل مكوّن.
- مجموعة أيقونات واحدة واضحة؛ لا تخلط أيقونات Material وemoji وأشكال أخرى بلا قرار.
- حالات: default، selected، focused، disabled، loading، error.
- أهداف لمس مناسبة للموبايل، labels مفهومة، ودلالة حالة لا تعتمد على اللون وحده.
- Light/Dark إن كانا في النطاق؛ راجع contrast من tokens ومن screenshots يرسلها المستخدم لاحقًا.

**تكييف Native:** استخدم أنماط التنقل والـsheet والـback المناسبة للمنصة، مع هوية خاصة للتطبيق. SwiftUI يمكن أن يستفيد من NavigationStack/List/TabView، وCompose من مكوّناته وأنماط تنقله، بما يناسب دعم الإصدارات. Native لا يعني أن الأيقونات أو الألوان يجب أن تظل افتراضية. إذا اختيرت أيقونات مخصصة، وحّد اللغة البصرية والأحجام، وأبقِ labels وإمكانية الوصول. لا تقلد لقطة مرجعية بوضع إحداثيات ثابتة للشاشة كلها.

العربية: سجّل هل التطبيق عربي أو متعدد اللغات. استخدم اتجاه النظام وleading/trailing أو start/end، واعزل البريد والأرقام والمعرّفات عند الحاجة، وراعِ تكبير الخط. لا تعتمد على عكس كل الرسوم؛ بعض الأيقونات اتجاهية وبعضها ثابت. أوضح للمستخدم أن هذه النقاط روجعت في الكود وأن معاينة الجهاز لم تُنفذ.

### شاشة قائمة المهام

عنوان واضح، وعدد/سياق مفيد، تبويبات أو فلاتر ذات معنى، إضافة واحدة واضحة، وقائمة قابلة للتمرير. كل صف: إتمام، عنوان، موعد إن وجد، أولوية ومشروع عند الحاجة. تجنب ازدحام كل الصفوف بكل metadata.

Today / Upcoming / All هي views على نفس البيانات إذا كانت هذه views معتمدة. لا تجعلها مخازن مستقلة. قسم Projects لا يكون نسخة ثانية من شاشة المهام بنفس الفعل؛ كل tab له هدف.

زر + فعل إنشاء، وليس قسمًا ملاحيًا فارغًا. إذا يوجد + داخل bottom navigation وفعل إضافة آخر، اكتب لماذا كلاهما مطلوب وما الاختلاف. إزالة التكرار تعتمد على تجربة الاستخدام المتفق عليها.

### محرر المهمة

عنوان، وصف اختياري، أولوية، موعد، مشروع حسب النطاق، وSave واحد واضح. الحقول scrollable. validation عند المستوى المناسب. خطأ حفظ لا يمسح draft. Keyboard وsafe areas تُراعى في الكود، وتظل المراجعة الفعلية للمستخدم.

### حالات الشاشة المطلوبة

| الحالة | شكلها وسلوكها |
|---|---|
| Loading | تقدم واضح دون قفزات layout أو انتظار مزيف |
| Empty | شرح قصير وأول فعل مفيد |
| No results | يحافظ على الفلتر/البحث ويعرض طريقة تعديلهما |
| Error | رسالة مناسبة + retry فعلي عند إمكانه |
| Offline | سياسة معلنة لما يعمل وما يحتاج اتصالًا |
| Saving | يمنع تكرار submission ويحتفظ بالقيم |
| Saved | القائمة/التفاصيل تعكس القيمة الحقيقية |
| Destructive action | confirmation أو استرجاع حقيقي حسب العقد |

### Settings وOnboarding وSplash

لا تترك Settings للنهاية ثم تضيف قائمة خيارات وهمية. نفّذ الخيارات التي تخدم النطاق مثل appearance، default view أو إدارة البيانات إذا لها سلوك حقيقي.

Onboarding عندما توجد قيمة يحتاج المستخدم فهمها، مختصر وقابل للتخطي ويحفظ completion. لا تعرضه بعد كل تشغيل. وفر replay فقط إذا كان ضمن القرار. Splash أثناء التهيئة الفعلية دون تأخير صناعي.

Login ليس شرطًا للتطبيق المحلي. لو مطلوب، عرّف restore/logout وإدارة الخطأ مبكرًا. زر Forgot password أو Google لا يظهر قبل تنفيذ العقد الخاص به.

## ١٠. الحركة، الرسومات واللوجو

الحركة توضح تغييرًا: إتمام مهمة، فتح محرر، انتقال، أو feedback. تكون قصيرة ومعتدلة وتحترم reduced motion. لا تجعل المستخدم ينتظر الاحتفال قبل متابعة العمل. Lottie يحتاج أصلًا مناسبًا وحاجة فعلية؛ ليس شرطًا للتميز.

احتفظ بالرسومات كأصول منفصلة عن النص والأزرار. الـmockup مرجع، والنصوص والعناصر التفاعلية تُنفذ كمكونات Native حقيقية.

إذا مطلوب PNG → SVG، استعن بطريقة التحويل المتخصصة: تحليل درجات الألوان والشفافية، حفظ الثنيات/الدرجات المهمة، تتبّع جيد، وفحص الحدود المشتركة على خلفيات مختلفة. لا تعتمد على silhouette score لإثبات جودة كل لون. سجل التكبيرات المرجعية ونقاط التقاء الأجزاء. اختيار صورتين متشابهتين بالحجم الصغير لا يثبت جودة الحواف.

قابلية تغيير لون اللوجو تتم بأجزاء/ألوان مسمّاة؛ لا تطبق tint واحدًا يزيل تفاصيل الأصل. SVG ملف مصدر؛ توافقه مع عرض الأصول يختلف حسب المنصة، فلا تفترض أنه يُعرض مباشرة بكل renderer. حضّر نسخة أصل مناسبة للأداة والهدف، وحافظ على المصدر القابل للتعديل. تغيير أيقونة التطبيق أو launch resources يحتاج مسار بناء/تثبيت مناسبًا؛ تعديل مصدر شاشة داخل التطبيق لا يثبت تحديث الأيقونة المثبتة.

افصل شاشة launch النظامية عن onboarding داخل التطبيق. Animation تكون في الواجهة الفعلية وبسلوك تهيئة واضح. لا تختلق انتظارًا لعرض اللوجو. قبل إضافة Lottie أو مكتبة حركة، قيّم الحركة الأصلية البسيطة المناسبة للمنصة؛ لا تربط هويتنا بنوع مكتبة.

## ١١. خطة checkpoints: نفّذ رأسيًا وبحجم صغير

كل checkpoint له هدف محدود ومخرج مفهوم. يتتابع: قراءة الحقيقة → قرار صغير → تنفيذ → static checks المسموحة → تحديث الحالة → تسليم. لا تفتح feature جديدة قبل إغلاق عيوب المرحلة الحالية أو تسجيل اعتماد خارجي يمنع جزءًا واضحًا منها.

| المرحلة | المطلوب | ينتهي عندما |
|---|---|---|
| 0: الحقيقة والنطاق | افحص المشروع، اجمع القرارات الحرجة، سجل حدود التشغيل | PRODUCT_BRIEF والنطاق وحدود المعاينة واضحون |
| 1: الرحلات والاتجاه | قائمة المهام + محرر، حالات الشاشة، tokens أولية | SCREEN_PLAN وقواعد الأفعال والهوية جاهزة للمراجعة |
| 2: الأساس الصغير | Feature folders، error types، تركيب الاعتماديات، أدوات الجودة | الهيكل له استخدام فعلي وstatic checks سليمة |
| 3: نموذج البيانات والحفظ | Task وعقود repo ومخزن واحد حقيقي | العمليات الأساسية موصولة والحفظ محدد؛ runtime غير مدّعى |
| 4: أول رحلة كاملة | list → create → saved list؛ loading/error/empty | الكود متكامل، لا TODO في سلوك إنشاء أساسي |
| 5: lifecycle | edit / completion / reopen، archive/delete المعتمد | قواعد mutation والتوقيت متسقة في البيانات وUI |
| 6: التنظيم | المشاريع/المواعيد/البحث والفلاتر المعتمدة | نفس مصدر البيانات، تعريف Today/Overdue ثابت |
| 7: الهوية والبداية | polish للأيقونات، Settings، motion، onboarding إذا مطلوب | الحركات والإعدادات لها معنى وسلوك محفوظ |
| 8: التسليم اليدوي | حدّث التعليمات وCURRENT_STATE وHANDOFF | أوامر تشغيل صحيحة، بيانات تجربة اختيارية، قائمة معاينة للمستخدم |
| 9: feedback المستخدم | حل screenshot/سلوك محدد يرسله المستخدم | إصلاح مركز وفحوصات الكود متكررة دون simulator من المساعد |
| لاحقًا | cloud/team/reminders/recurrence/offline sync حسب الطلب | عقد كل ميزة معتمد قبل تنفيذها |

عند الحاجة إلى backend/auth، أضف checkpoint مبكرًا بعد العقود وقبل تركيب الواجهة عليه. لا تبنِ UI ينادي API متخيلًا ثم تحاول مطابقة backend في النهاية.

في كل مرحلة قدّم تقريرًا قصيرًا ثم أكمل المهمة المفوضة. لا تطلب موافقة لكل refactor صغير، ولا تعتبر كل checkpoint إذنًا لزيادة نطاق المنتج.

## ١٢. Clean code: قواعد قابلة للمراجعة

- أسماء تصف سلوكًا أو مفهومًا؛ لا تستخدم Manager/Helper عام إذا المسؤولية محددة.
- function لها سبب واحد، وView أو composable له تركيب واضح. قسّم عند اختلاف المسؤولية أو صعوبة القراءة، وليس طبقًا لرقم أسطر سحري.
- لا تنسخ validation أو rules أو queries بين الشاشات. مكان واحد للقاعدة المشتركة.
- استخدم typed enums/inputs/failures بدل strings عامة وbooleans غير مفهومة.
- null يمثل حالة محددة؛ لا تستخدم تاريخًا مزيفًا أو projectId فارغًا كبديل عن عدم وجودهما.
- errors لا تُبتلع بصمت؛ تُحوّل لما تستطيع الواجهة التعامل معه.
- لا logging لكلمات السر أو tokens أو بيانات خاصة. لا تعرض raw exception للمستخدم.
- الاشتراكات/controllers تُغلق حسب lifecycle. لا request يتأخر ويكتب نتائج بحث قديم فوق بحث أحدث.
- لا تؤسس generic base classes وطبقات services لكل شيء من غير حاجة فعلية.
- التعليقات تشرح السبب والقاعدة غير الواضحة، لا تعيد كتابة أسماء الدوال.
- أوصل production composition فعلًا: class جديد غير مستخدم ليس تنفيذًا مكتملًا.

### مراجعة قبل إغلاق أي checkpoint

هل الواجهة تستدعي contract مناسبًا؟ هل DTO بقي في data؟ هل operation failure يحافظ على draft؟ هل repository وcontroller متفقان على أنواع النتيجة؟ هل caller تم تحديثه بعد تغيير constructor؟ هل العنصر الذي يظهر للمستخدم محفوظ أم فقط مضاف للقائمة في الذاكرة؟

**درس constructor:** في مشروع الشات اختلفت أسماء named parameters عن call sites. القاعدة العامة هنا: بعد تغيير initializer أو constructor أو argument label راجع كل مواضع الإنشاء والعقد، ولا تعالج الأعراض بإضافة arguments متناقضة. تحقق الأنواع الكامل ينتظر مسار compilation المسموح به.

## ١٣. التحقق السريع المسموح

الافتراضي مراجعة المصادر وفحوص خفيفة متاحة؛ لا Simulator ولا تشغيل التطبيق ولا بناء native ولا اختبارات. وثّق فرق «تمت مراجعة الكود» و«تم إثبات السلوك بالتشغيل». هذه سياسة تقدم طلبها المستخدم، وليست بديلًا عن قبول إصدار مكتمل؛ يلزم دليل بناء وتجربة قبل وصف التطبيق بأنه جاهز للإصدار.

### iOS: Swift/SwiftUI

افحص هل swift-format أو SwiftLint متاح ومهيأ بالفعل. استخدم check/lint بصيغته المدعومة في النسخة المحلية، ولا تخترع config أو أمرًا افتراضيًا. لو الأداة غير موجودة، سجّل ذلك وراجع الكود؛ لا تبدأ تثبيتًا كبيرًا أو xcodebuild لمجرد تعويض غياب lint. تحليل syntax إن توفر يفحص تركيب اللغة، ولا يثبت صحة الأنواع أو macros أو frameworks أو deployment target. Xcode Preview قد يبني التطبيق؛ لا تفتحه كطريقة ملتوية لتنفيذ بناء ممنوع.

### Android: Kotlin/Compose

اقرأ Gradle wrapper وcatalog والإعدادات الحالية. ktlint/detekt يمكن استخدامهما إذا كانا موجودين ومهيأين. افحص task قبل تشغيله: بعض Gradle tasks تُحمّل dependencies أو تتطلب SDK/compilation؛ اسم lint لا يثبت أنه سريع أو منفصل عن البناء. لا تبدأ Gradle assemble/install أو Emulator تلقائيًا. لا تنسخ أرقام Kotlin/Compose/AGP من مثال قديم؛ توافق الأدوات جزء من إعداد المشروع.

### Backend، إذا كان ضمن النطاق

اقرأ scripts الفعلية بدل تخمين الأوامر. format check وlint وtypecheck أدوات مناسبة عندما تكون مهيأة. dependency install يتبع lockfile ومدير الحزم. build غير native يُشغّل عندما طلب المستخدم التحقق به أو احتاجه تسليم مفوض. Node/Nest ليسا شرطًا لتطبيق Native محلي.

| الدليل الموجود | ما يثبته | ما لا يثبته |
|---|---|---|
| مراجعة النص والمراجع | اتساق مرئي في المصادر | compilation أو تشغيل |
| formatter/linter | اجتياز القواعد التي شغّلتها | صحة جميع الأنواع أو حفظ البيانات |
| compiler/build ناجح على نسخة محددة | قابلية بناء تلك النسخة بتلك البيئة | جودة UX أو صحة كل رحلة |
| تجربة المستخدم للرحلة | السلوك الذي شاهده في النسخة المجربة | كل حالات الخطأ أو كل الأجهزة |
| CI | الخطوات الفعلية التي نفذها على SHA محدد | خطوات لم تُدرج فيه |

إذا CI ضمن المطلوب، خلي خطواته read-only/reproducible وبصلاحيات read عندما تكفي. format:check وlint لا يصلحان الملفات في CI. لا تضف diagnostic uploads أو بيانات خاصة. آخر حالة ناجحة مرتبطة بالـcommit الذي فُحص، لا باسم branch فقط.

### إذا طلب المستخدم الاختبارات

اختر عددًا محدودًا حول المخاطر الحقيقية: mutation/persistence، قواعد التاريخ، فشل الحفظ، صلاحيات الوصول لو backend موجود. أعد استخدام suites الموجودة قبل إنشاء suites جديدة. لا تجعل البحث عن تغطية شاملة يمنع تقدم checkpoint صغير.

في Nest: لو runner يعتمد على decorator metadata، راجع هل يشغّل الـcompiled app أم transpilation تُسقط metadata. عند hang افحص setup/teardown وموارد DB وعمليات runner والتوازي. تشغيل suites في processes منفصلة حل محتمل بعد فهم العزل، وليس إعدادًا يُنسخ لأي مشروع تلقائيًا.

أبلغ بنتيجة واقعية: الأمر، الكود الذي فُحص، نجح/فشل، وما لم يُفحص. فحص static نظيف لا يثبت runtime persistence أو native layout.

## ١٤. الإنجاز وإدارة الوقت

اشتغل بأصغر شريحة تنتج سلوكًا كاملًا. لا تقضِ المهمة كلها في اختيار frameworks، ولا تبدأ أكثر من migration/build/runner لنفس المشروع.

- قبل العمل: قل الهدف الحالي في جملة.
- خلال العمل الطويل: تحديث مفيد كل نحو دقيقة، يوضح ما نُفذ أو سبب انتظار فعلي.
- لو خطوة تحتاج تنزيلًا كبيرًا أو إعداد native طويلًا: لا تبدأها ضمن static-only. سجّل الحاجة وخطوتها للمستخدم إذا طلب التشغيل.
- لو فحص مسموح علق: اقرأ آخر output وحالة العملية وdeadline؛ حدّد السبب قبل retry. لا تضف sleep متكررًا كحل دائم.
- لا تكرر نفس العملية غير المتغيرة بلا دليل جديد، ولا تخفي failure بتخطي dependency/typecheck.
- لو البيئة تمنع جزءًا، أكمل العمل المستقل الممكن، ثم سلّم ما بقي بدقة.

قبل تغيير أمر التشغيل أو SDK أو DB، راجع الموجود. خطأ connection قد يكون خدمة متوقفة أو process معلقة أو URL خاطئًا؛ لا تعِد كتابة auth قبل معرفة السبب.

## ١٥. Git وbranches لو موجودة

HEAD الفعلي source of truth. افحص base branch والـdiff والملفات غير المنشورة. إذا هناك stack، اعرف dependencies قبل cherry-pick أو branch جديد. أنشئ commit صغيرًا متعلقًا بالمرحلة عندما يكون ذلك ضمن التفويض.

لا تضم platform auto-migrations أو ملفات generated غير مقصودة مع polish UI. stage الملفات المقصودة تحديدًا. لا تنقل تغييرات من branch موازٍ بمجرد اسمه؛ قارن المفيد الذي لم يصل إلى HEAD وتأكد من صلاحية config الحالي.

عند PR مفوض: العنوان واضح، base صحيح، body يذكر ما تغير ودليل التحقق وحدوده. سجل SHA/run الحقيقي. PR يستحق Ready وفق شروط مراجعة المشروع، لا لمجرد نجاح analyzer. لا تندمج تلقائيًا.

ضع نتائج فحص commit التوثيق الأخير في PR metadata عند الحاجة، دون محاولة كتابة SHA الملف داخل نفسه.

## ١٦. قالب CURRENT_STATE

استخدم بيانات فعلية؛ unknown أفضل من اختلاق حالة. عدّل الملف قبل نهاية كل checkpoint.

```text
Current phase:
Project path:
Branch / HEAD:
Approved scope:
Locked decisions:
Completed behaviors:
Implemented but runtime-unverified:
Verification actually performed:
CI run + tested SHA (if applicable):
User changes preserved:
Local processes started by explicit request:
Known issues:
Deferred features:
Native / visual review: user-owned; pending unless user supplied evidence
Exact next checkpoint:
```

اقرأ هذا الملف عند استئناف العمل، ثم قارنه بالـHEAD والملفات. إذا أصبح وصف قديم غير صحيح، عدّله بدل إضافة سطر جديد يناقضه.

## ١٧. قالب تقرير التسليم

التقرير موجّه لشخص يستطيع متابعة المشروع، وليس استعراضًا للتفاصيل التقنية.

1. ما تم تنفيذه، وما فائدته للمستخدم.
2. الملفات الأساسية والقرار المعماري وسببه.
3. branch / PR / commits إذا موجودة.
4. الفحوصات الفعلية ونتائجها وSHA أو حالة الملفات التي فُحصت.
5. ما لم يُنفذ: خصوصًا Simulator/runtime/native acceptance.
6. الأخطاء أو الدين التقني المعروف، وما يحتاجه الجزء التالي.
7. طريقة تشغيل المستخدم إذا طلبها؛ الأوامر متوافقة مع مشروعه وSDK الفعلي.
8. الخطوة التالية المحددة، لا قائمة ميزات عشوائية.

اكتب ملفات الشرح العربية بـRTL صحيح، واعزل paths/commands/English كـLTR. Cairo مناسب للدليل إذا متاح أو مضمن، ولا يعني اختياره أن التطبيق نفسه يجب أن يستخدمه.

## ١٨. قائمة المعاينة التي ينفذها المستخدم

هذه ليست أمرًا للمساعد بتشغيل التطبيق. سلّمها عندما يطلب المستخدم تجربة التطبيق:

- افتح التطبيق: هل التهيئة والحالة الفارغة مفهومتان؟
- أنشئ مهمة بعنوان عربي/إنجليزي طويل ووصف متعدد الأسطر.
- جرّب عنوانًا فارغًا ثم حفظًا صحيحًا؛ هل القيم محفوظة بعد خطأ؟
- عدّل نفس المهمة، أكملها وأعد فتحها.
- اختبر اليوم/المتأخر/موعد غائب وفق العقد.
- أغلق التطبيق وافتحه للتأكد من بقاء البيانات أو session إذا موجودة.
- ابحث بنتيجة وبدون نتيجة، وغيّر الفلاتر ثم ارجع.
- جرّب الخط الكبير، لوحة المفاتيح، Light/Dark إن كانا منفذين.
- غيّر Settings ثم أعد التشغيل؛ هل السلوك والاختيار محفوظان؟
- عند backend: اختبر انقطاع الاتصال وretry حسب السياسة، دون افتراض offline sync.

أي screenshot أو نتيجة يرسلها المستخدم تُربط بالنسخة التي جرّبها. أصلح العيب المحدد، وواصل static checks، واترك المعاينة التالية له.

## ١٩. الأخطاء السابقة وتحويلها إلى قواعد

| التجربة | الخطأ أو الخطر | القاعدة التي تمنع تكراره |
|---|---|---|
| حالة محادثة قديمة | العمل على تصور يتأخر عن HEAD | قراءة HEAD/status وCURRENT_STATE أولًا |
| branches متوازية | نقل config قديم أو duplicating foundation | مقارنة الفرق وتكييف الجزء المطلوب |
| E2E hang | suites وموارد لا تُغلق أو metadata ناقصة | diagnosis محدد، عزل صحيح، compiled artifact عند الحاجة |
| SDK مختلف | PATH أقدم من متطلبات المشروع | فحص SDK وIDE قبل تعديل manifest |
| concurrent native builds | الانتظار والتكرار من أكثر من process | native للمستخدم؛ لا تشغيل موازي من المساعد |
| API تفتح port ولا ترد | الاستماع لا يثبت الصحة | health/response تحقق فعلي عند تفويض التشغيل |
| UI وظيفية مختلفة عن المرجع | اعتبار التنفيذ الوظيفي قبولًا بصريًا | UI direction + screen plan + user screenshots |
| زر + وتبويب متشابهان | duplicate actions مربكة | لكل فعل هدف واضح؛ navigation مختلف عن action |
| Settings/Onboarding منسية | اكتمال feature list دون بداية/إعدادات | screen inventory مبكر وسلوك محفوظ |
| صورة تتحول Vector | انكشاف طبقة غامقة وتموج الحواف | مراجعة internal colors والجوانب المشتركة والتكبيرات |
| Git workspace متغير | نشر platform migration مع تغيير صغير | staging محدد وتسليم يذكر local differences |
| تقارير قبول عامة | CI أخضر يوحي بأن التطبيق مُعاين | افصل source/static/CI/runtime/visual/user acceptance |
| طول العمل | خطوات setup لا تخدم checkpoint الحالي | شريحة صغيرة وتحديثات مفيدة وحدود تشغيل واضحة |

## ٢٠. نموذج التكليف لكل checkpoint

انسخ هذا القالب بدل إرسال «كمل التطبيق كله» مع سياق مبهم:

```text
نفّذ checkpoint: [اسم المرحلة].
اقرأ CURRENT_STATE وراجع HEAD/status أولًا.
الهدف: [رحلة أو سلوك محدد].
داخل النطاق: [٣–٥ بنود].
خارج النطاق الآن: [التوسعات المؤجلة].
معيار الانتهاء: [سلوك وملفات وفحوصات مسموحة].
التشغيل: static-only؛ لا Simulator ولا native build ولا app run.
الاختبارات: لا تضف أو تشغّل اختبارات إلا إذا طلبتها صراحة.
حافظ على تغييرات المستخدم ولا تبدأ نشرًا غير مفوض.
في النهاية حدّث CURRENT_STATE وأرسل تقريرًا واضحًا وخطوة تالية واحدة.
```

### مثال تكليف أول رحلة

```text
نفّذ رحلة إنشاء مهمة كاملة وفق النطاق المعتمد.
المطلوب: عنوان مطلوب، وصف اختياري، Save، حفظ بالمخزن المتفق عليه،
تحديث القائمة، validation، saving/error/empty states.
راجع caller/constructor types وتركيب الاعتماديات الفعلي.
لا تضف recurrence أو reminders أو فريق أو مزامنة أو auth جديدًا.
أكمل static checks المسموحة وحدّث CURRENT_STATE.
لا تشغّل التطبيق؛ المستخدم هو من سيجربه.
لا تدّعِ نجاح persistence عبر إعادة التشغيل قبل وجود دليل runtime.
```

## خلاصة موجهة للمساعد

افهم المنتج، ثبّت النطاق، ابنِ حدودًا بسيطة تخدم العمل الحالي، ثم نفّذ رحلة كاملة في كل checkpoint. حافظ على البيانات والهوية البصرية والقرارات. فحص الكود وظيفتك، تشغيل التطبيق ومعاينته للمستخدم. احفظ المكان الذي وصلت إليه في المشروع، وقل بدقة ما تم وما لم يتم.

## ٢١. قواعد إضافية لمنع التخمين أثناء التنفيذ

### دورة العمل لكل مهمة صغيرة

1. اقرأ CURRENT_STATE والتعليمات والملفات التي تعتمد عليها المهمة.
2. اكتب في سطرين المدخل والمخرج والطبقة التي ستتغير.
3. راجع تعريف النوع أو الدالة قبل كتابة استدعاء لها؛ لا تفترض أسماء API.
4. نفّذ تغييرًا يخدم الرحلة كاملة، وحدّث call sites وتركيب الاعتماديات.
5. راجع diff وما إذا كان لمس ملفات مستخدم أو generated files بالخطأ.
6. نفّذ الفحص الخفيف المسموح والمتاح وسجّل اسمه ونتيجته.
7. حدّث CURRENT_STATE مع خطوة تالية محددة.

لا تترك ملفات متناقضة وتكتب «سنصلح لاحقًا» لقلب الرحلة. إذا كان API غير واضح، اقرأ تعريفه أو الوثائق الرسمية للنسخة؛ لا تكتب عدة محاولات عشوائية وتنتظر أن يحل المستخدم أخطاء البناء.

### عقد عمليات أول رحلة: مثال مستقل عن اللغة

```text
CreateTaskInput:
  title: required, trimmed
  description: optional
  priority: approved enum
  dueDate: optional calendar date
  projectId: optional stable ID

create(input): saved TaskItem or defined failure
setCompleted(id, completed): saved TaskItem or defined failure

Presentation:
  editing -> saving -> success OR editing with error
  preserve draft on failure
  prevent duplicate save while saving
  dismiss editor only after confirmed save
  show returned stored item, not an assumed copy
```

إذا mutation تكتمل بعد إغلاق الشاشة، حدّد هل الحفظ يستمر أو يُلغى، ومن يستقبل النتيجة. لا تجعل إغلاق الواجهة يخلق عملية مجهولة أو يحذف draft بلا قرار. اختر refresh بعد mutation أو observation للمخزن، وتجنب إضافتهما بطريقة تنتج صفوفًا مكررة.

### قابلية التوسع دون تجهيزات مبكرة

ابدأ بمصدر بيانات واحد وعقود صغيرة. استخدم IDs ثابتة لقوائم SwiftUI/Compose، وعرضًا مناسبًا للقوائم بدل بناء كل الصفوف داخل حاوية غير كسولة. لا تنفذ I/O متزامنًا على خيط UI. عند تضخم البيانات راجع indexes والبحث وحدود تحميل القائمة بناءً على حاجة فعلية. لا تحمّل كل التاريخ من backend بلا حدود. لا تضف cache/outbox/event bus لمجرد احتمال نمو التطبيق.

### عندما تُضاف التذكيرات أو التكرار لاحقًا

التذكير يحتاج تحديد موعد ومنطقة زمنية وسياسة إذن الإشعارات، وما يحدث عند تعديل/حذف/إتمام المهمة أو رفض الإذن. لا تعرض «تم تفعيل التذكير» قبل نجاح جدولة حقيقية. API الأذونات والجدولة تتراجع من وثائق المنصة وقت ذلك checkpoint.

التكرار يحتاج تحديد هل ننشئ instance جديدة أم نعيد فتح نفس المهمة، تاريخ الأساس، نهاية التكرار، وكيفية التعامل مع مهمة متأخرة. لا تضف boolean اسمها recurring وتعتبر الميزة مكتملة. البيانات الجديدة تحتاج migration تحفظ بيانات المستخدم.

### ملف السؤال والتقرير في كل مرحلة

السؤال يكون عن قرار مؤثر لم يُحسم؛ لا تسأل «أكمل؟» بعد كل دالة. إذا المستخدم فوّض المرحلة، أكملها دون توسيع النطاق. عند توقف بسبب قرار لازم، سلّم العمل المستقل الذي انتهى وما يتوقف على الإجابة.

التقرير المختصر:

```text
Checkpoint:
Implemented:
Why it matters:
Files changed:
Checks run + exact result:
Not checked / user runtime review pending:
Known issue:
CURRENT_STATE updated:
Next single checkpoint:
```
